<Warning>
  **In development.** 86d is being built in the open. Every capability is Experimental until it earns evidence, so check [maturity levels](/resources/versioning) before you rely on anything here.
</Warning>

Every [Feature](/resources/glossary#feature) in 86d is a [Module](/concepts/modules), including every first-party entry in the generated registry. There is no privileged internal API: what you write gets the same treatment as `@86d-app/products`. Your Module can add [Storefront](/concepts/storefront) components, [Store Admin](/concepts/admin) pages, and API endpoints.

Data-bearing Module authoring is mid-migration. Most first-party Modules still expose legacy `Module.schema` field maps, and the migrated subset feeds those maps through `transcodeModuleSchema` into compiled `tables`. The JSON storage path is gone, but native Zod declarations and Postgres role isolation are not yet the supported external authoring contract.

## Scaffold it

<Steps>
  <Step title="Create the package">
    ```bash
    86d module create my-feature
    ```

    You get a package and surface scaffold under `modules/my-feature/`:

    ```text
    modules/my-feature/
    ├── package.json
    ├── tsconfig.json
    └── src/
        ├── index.ts                 Module factory
        ├── schema.ts                Legacy migration placeholder
        ├── mdx.d.ts                 MDX type declarations
        ├── store/
        │   ├── components/mdx.tsx
        │   └── endpoints/routes.ts
        ├── admin/
        │   ├── components/.gitkeep
        │   └── endpoints/routes.ts
        └── __tests__/
            └── index.test.ts
    ```
  </Step>
  <Step title="Preview the target storage declaration">
    The current CLI scaffold still emits legacy `schema` wiring. For a current storage-free experiment, remove the generated `schema` import and `Module.schema` property. In the future contract, every Module instead declares `storage: { kind: "none" }`, `storage: { kind: "config", ... }`, or `storage: { kind: "relational", ... }`. The following Relational declaration shape uses imports that resolve today, but data-bearing external Modules should not rely on it until the Module storage and isolation migration closes.

    ```ts src/declaration.ts
    import { col, type TableDeclaration } from "@86d-app/core/schema";
    import { z } from "@86d-app/core/zod";

    export const itemShape = z.object({
      id: z.uuid().register(col, { pk: true }),
      title: z.string().max(200),
      published: z.boolean().default(false),
    });

    export const itemTables = {
      item: { shape: itemShape },
    } satisfies Readonly<Record<string, TableDeclaration>>;
    ```

    The target entrypoint wires `storage: { kind: "relational", tables: itemTables }` and omits `Module.schema`. The current compatibility adapter is migration code, not a pattern for new Modules.
  </Step>
  <Step title="Write endpoints">
    Add controllers and endpoints. Store endpoints are public. Admin endpoints sit under `/api/admin/...` and require an authenticated Store Admin session, enforced for you.
  </Step>
  <Step title="Enable it">
    ```bash
    86d module enable my-feature
    ```

    This adds `@86d-app/my-feature` to your active [Template](/concepts/templates)'s `config.json`.
  </Step>
  <Step title="Regenerate">
    ```bash
    86d generate
    ```

    Your Module is now imported statically, its endpoints are mounted under `/api/`, and its components are in the MDX registry.
  </Step>
  <Step title="Run the tests">
    ```bash
    bun test
    ```

    The starter test only checks that the factory returns the expected `id` and `version`. Replace it with coverage of what your Module actually does, including what it does when a dependency is unavailable.
  </Step>
</Steps>

## Target entry point

<Warning>
  **Future contract.** This uses valid package subpath imports, but native storage authoring is not current until the Module storage and isolation migration closes.
</Warning>

`src/index.ts` will export a factory that returns a `Module` with an explicit Relational storage declaration:

```ts src/index.ts
import type { Module, ModuleConfig } from "@86d-app/core/types/module";
import { itemTables } from "./declaration.js";
import { storeEndpoints } from "./store/endpoints/routes.js";
import { adminEndpoints } from "./admin/endpoints/routes.js";

export default function myFeature(
  options: ModuleConfig = {},
): Module {
  return {
    id: "my-feature",
    version: "0.0.1",
    storage: {
      kind: "relational",
      tables: itemTables,
    },
    options,
    endpoints: {
      store: storeEndpoints,
      admin: adminEndpoints,
    },
  };
}
```

It is a factory rather than a singleton so a Store can pass it options through `moduleOptions` in `config.json`.

## Where your admin pages appear

Declare a group and your pages land in the Store Admin sidebar. The nine top-level groups are **Catalog**, **Sales**, **Customers**, **Fulfillment**, **Marketing**, **Content**, **Finance**, **Support**, and **System**.

Each has collapsible subgroups, such as Sales → Orders, Cart, Billing. Name one with `subgroup` on an `AdminPage`:

```ts
admin: {
  pages: [
    {
      path: "/admin/my-feature",
      component: "MyFeatureList",
      label: "My feature",
      icon: "Star",
      group: "Catalog",
      subgroup: "Products",   // optional, overrides the default mapping
    },
  ],
},
```

## Talking to another Module

Cross-Module work uses typed capabilities for immediate decisions. Cross-Module reads use published column-projected views granted at provision time (target). Legacy `exports` and `requires` field metadata remains during migration; it does not grant table access.

```ts
capabilities: {
  accepts: [acceptCapability(someCapability)],
},
```

The runtime validates contracts at startup. A missing capability fails at boot, not on a shopper request.

## Reaching the database

**Current migration:** database access goes through [`ModuleDataService`](/resources/glossary#moduledataservice) as `ctx.data`. It reaches compiled `mod_<moduleId>` tables for Modules that expose adapter-produced `tables`; most first-party Modules remain legacy-only and are reported as not transcoded. There is no JSON fallback.

**Target:** every Module declares an explicit storage kind. A Relational Module declares native Zod `tables` and/or `extends` with `col`, while Config and None receive only their compiled bounded interfaces. The same data service runs under that Module's Postgres role. Until that migration closes, current storage-free Modules and surface work are the stable authoring path; treat data-bearing examples on this page as a preview.

A Module never imports `@86d-app/db` or an ORM client directly:

```ts
init: async (ctx: ModuleContext) => {
  // ctx.data is a ModuleDataService scoped to this module's schema
  const controllers = createControllers(ctx.data);
  return { controllers };
},
```

`@86d-app/core/test-utils` gives you an in-memory data service, so your unit tests need no database at all.

## Publishing to npm

Anyone running 86d can install your Module once it is published:

<Steps>
  <Step title="Update package.json">
    Set `"private": false`, pick a version, and write a `description` and `keywords` someone can find.
  </Step>
  <Step title="Build">
    ```bash
    bun run build
    ```
  </Step>
  <Step title="Publish">
    ```bash
    npm publish --access public
    ```

    First-party Modules ship through Changesets with npm provenance. If you publish your own, that release and security process is yours to run.
  </Step>
</Steps>

Then anyone installs it with:

```bash
86d module add npm:@your-scope/your-module
```

Publishing puts your package on npm. It does not add it to the first-party registry, and it says nothing about compatibility or maturity. Anyone installing it should read it first, and so should you.
