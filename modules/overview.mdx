<Warning>
  **Experimental.** All 101 entries currently publish as Experimental with no recorded evidence. Being in this catalog says nothing about whether a Module works. See [maturity levels](/resources/versioning).
</Warning>

Your Store does what the [Modules](/concepts/modules) you enabled make it do. Everything below is first-party, MIT-licensed, and already sitting in the repository you cloned. Nothing is on until you turn it on, and a Module you never enable adds no routes, no tables, and no attack surface.

Pick from the groups below, read the page for anything you plan to keep, then list it in `config.json` and regenerate.

The machine-readable list, with pinned commits and integrity hashes, is the [registry manifest](https://github.com/86d-app/86d/blob/main/apps/registry/registry.json).

## Installing one

Use the [CLI](/cli/overview):

```sh
86d module add module_name_here
```

The CLI downloads the Module, installs its dependencies, and enables it in your active [Template](/concepts/templates). Editing `config.json` by hand does the same thing. Either way, run `86d generate` or its endpoints and [Storefront](/concepts/storefront) components will not exist.

Every entry needs its exact package name in `modules`, plus the versioned Experimental opt-in. A `"*"` wildcard, or no `modules` field at all, admits nothing. See [turning on an Experimental Module](/configuration/store-config#turning-on-an-experimental-module).

Managed provisioning admits a curated default set without promoting those Modules past Experimental. Maturity still comes from registry evidence, not from being included at provision.
